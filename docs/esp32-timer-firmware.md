## 2. Why this change is needed

The current ESP200 firmware already runs several timers, but its timer format is missing what the app needs to manage them safely.

| | Current firmware (verified) | App needs (Timer API v2) |
|---|---|---|
| Create | `/timer?relay=1&seconds=600` turns the relay **ON immediately** and OFF after 600 s. `action` is ignored. | `/timer?relay=1&action=off&seconds=600` does **nothing now**; sets the relay to `action` when the timer fires. |
| Timer entry in `/status` | `{"relay":1,"seconds":600,"remaining":412,"repeat":false}` — **no `id`, no `action`** | `{"active":true,"id":7,"relay":1,"action":"off","repeat":false,"seconds":600,"remaining":412}` |
| Cancel one | Not possible | `/timer/cancel?id=7` |
| Cancel a relay's timers | `/timer/cancel?relay=1` | keep this |
| List timers | `/timers` → **404** | `/timers` → list |
| Clear | `/timers/clear` **ignores `?relay` and wipes every timer** | `/timer/clear` (all) or `/timer/clear?relay=1` (one relay); `/timers/clear` must respect `?relay` too |
| Version flag | none | `"timerApi": 2` in `/status` |

### What the app does until the firmware is updated

The app detects the firmware by the `"timerApi"` field in `/status`:

- **`timerApi` missing ("basic" mode, today's firmware):** the app shows running timers as *Turn OFF in …*, offers **Cancel Timers on This Relay** (`/timer/cancel?relay=N`), and **refuses to create timers**. Creating one on this firmware would switch the relay ON straight away, which is unsafe for mains equipment. It never calls `/timers/clear`.
- **`timerApi: 2` ("full" mode):** the app unlocks the full timer UI automatically. No app change or redeploy is needed.

## 3. Endpoints that must stay unchanged

These already work and the app depends on them. Keep their paths, parameters and response shapes.

| Endpoint | Behaviour |
|---|---|
| `GET /on?relay=1` / `GET /on?relay=2` | Relay ON. Response `{"ok":true,"relay":1,"power":"on"}` |
| `GET /off?relay=N` | Relay OFF. Response `{"ok":true,"relay":N,"power":"off"}` |
| `GET /toggle?relay=N` | Toggle the relay |
| `GET /status` | Device status (extended below with `timerApi` and richer timer entries) |
| `HEAD /` or `GET /` | Returns 200 (the app uses this as a connection test) |

`/status` today returns, and must keep returning:

```json
{
  "ok": true,
  "device": "ESP200",
  "relays": [
    { "relay": 1, "power": "off" },
    { "relay": 2, "power": "on" }
  ],
  "timers": [],
  "uptime": 18572,
  "ip": "192.168.1.200",
  "ssid": "Dhanush-Wifi-2.4G",
  "rssi": -53
}
```

Manual `/on`, `/off` and `/toggle` must **never** cancel or change any timer.

## 4. Timer API v2

### 4.1 Timer object

Every timer, wherever it appears (`/status`, `/timers`, the `/timer` response), uses this shape:

```json
{
  "active": true,
  "id": 7,
  "relay": 1,
  "action": "off",
  "repeat": false,
  "seconds": 3600,
  "remaining": 2841
}
```

| Field | Type | Meaning |
|---|---|---|
| `active` | boolean | Always `true` for listed timers. Finished or cancelled timers are removed from lists. |
| `id` | integer | Unique id generated by the ESP32. Unique since boot, **never reused**. |
| `relay` | integer | `1` or `2`, the relay this timer switches. |
| `action` | `"on"` \| `"off"` | The state to **set** when the timer fires. It is not a toggle. |
| `repeat` | boolean | `true` means the timer re-arms and runs again every `seconds`. |
| `seconds` | integer | The configured duration or interval, 1–86400. |
| `remaining` | integer | Whole seconds until the next time it fires, ≥ 0. |

### 4.2 `GET /status` (extended)

Add `"timerApi": 2`, and list all active timers for all relays using the timer object above:

```json
{
  "ok": true,
  "device": "ESP200",
  "timerApi": 2,
  "relays": [
    { "relay": 1, "power": "on" },
    { "relay": 2, "power": "off" }
  ],
  "timers": [
    { "active": true, "id": 1, "relay": 1, "action": "off", "repeat": false, "seconds": 3600, "remaining": 2841 },
    { "active": true, "id": 2, "relay": 2, "action": "on",  "repeat": false, "seconds": 1800, "remaining": 1022 },
    { "active": true, "id": 3, "relay": 1, "action": "on",  "repeat": true,  "seconds": 600,  "remaining": 421 }
  ],
  "timerCount": 3,
  "uptime": 123456,
  "ip": "192.168.1.200",
  "ssid": "Dhanush-Wifi-2.4G",
  "rssi": -58
}
```

`"timerApi": 2` is what tells the app it's safe to create timers. Only add it once every rule in this document is implemented.

### 4.3 `GET /timer` — create a timer

```
GET /timer?relay=1&action=off&seconds=3600
GET /timer?relay=2&action=on&seconds=1800
GET /timer?relay=1&action=on&seconds=600&repeat=true
```

| Parameter | Required | Values |
|---|---|---|
| `relay` | yes | `1` or `2` |
| `action` | yes | `on` or `off` |
| `seconds` | yes | integer 1–86400 |
| `repeat` | no | `true` (anything else, or missing, means one-time) |

Behaviour:

- **Do not change the relay when the timer is created.** Only the timer is scheduled.
- Adds a **new** timer. Existing timers keep running, including ones on the same relay.
- Maximum **10 active timers** per ESP32, across both relays.

Success (HTTP 200):

```json
{
  "ok": true,
  "relay": 1,
  "timer": { "active": true, "id": 7, "relay": 1, "action": "off", "repeat": false, "seconds": 3600, "remaining": 3600 }
}
```

The app stores `timer.id` so it can cancel this exact timer later.

### 4.4 `GET /timers` — list timers

```
GET /timers              -> all timers
GET /timers?relay=1      -> only relay 1 (optional filter)
```

```json
{ "ok": true, "timers": [ { "active": true, "id": 7, "relay": 1, "action": "off", "repeat": false, "seconds": 3600, "remaining": 2841 } ], "count": 1 }
```

### 4.5 `GET /timer/cancel` — cancel timers

```
GET /timer/cancel?id=7        -> cancel exactly timer 7
GET /timer/cancel?relay=1     -> cancel every timer on relay 1 (keep today's behaviour)
```

- With `id`: 200 `{"ok":true,"cancelled":[7]}`, or 404 if no active timer has that id.
- With `relay`: 200 `{"ok":true,"cancelled":[3,7]}` (the list may be empty).
- With neither parameter: 400.
- Cancelling never changes the relay state.

### 4.6 `GET /timer/clear` — clear timers

```
GET /timer/clear             -> cancel ALL timers on this ESP32
GET /timer/clear?relay=2     -> cancel only relay 2's timers
```

Response: `{"ok":true,"cancelled":[...],"count":0}`.

The existing **`/timers/clear` must behave the same way and must respect `?relay`.** Today it ignores `?relay` and wipes everything, which is how timers were lost by accident. Invalid relay values (for example `?relay=9`) must return **400** and cancel nothing.

## 5. Timer behaviour rules

1. **Target state, not toggle.** When a timer fires, set the relay to `action`. If the relay is already in that state, do nothing (idempotent).
2. **Creation doesn't switch anything.** `/timer` only schedules.
3. **Independent timers.** Up to 10 timers run at once, in any mix of relays, actions and repeat settings. Example that must work simultaneously:
   - Relay 1 (Light): OFF after 1 hour
   - Relay 2 (Fan): ON after 30 minutes
   - Relay 1 (Light): ON every 10 minutes (repeat)
   - Relay 2 (Fan): OFF after 2 hours
4. **Repeat is interval-based.** `action=off&seconds=600&repeat=true` means: after 10 min → OFF, after another 10 min → OFF, and so on. It never alternates ON/OFF.
5. **No drift on repeat.** Re-arm from the scheduled fire time (`dueAt += seconds * 1000`), not from "now", so a repeating timer doesn't slowly drift.
6. **Manual control never cancels timers.** `/on`, `/off` and `/toggle` leave all timers running. Example: "OFF after 1 hour" is set, the user turns the relay ON manually, and after the hour the ESP32 still sets it OFF.
7. **Same fire time.** If two timers on the same relay fire in the same loop, run them in order of `id` (oldest first); the last one decides the final state.
8. **IDs.** Start at 1 after boot and increase by 1 per created timer. Never reuse an id, even after it is cancelled or fires.
9. **Reboot or power loss clears all timers.** That's acceptable. The app treats `/status` as the source of truth and never re-creates timers on its own. Optional later improvement: persist timers with NTP time and `Preferences`.
10. **Non-blocking.** Never use `delay()` for timers. The web server must keep answering while timers run.

## 6. Errors

All errors are JSON: `{"ok": false, "error": "<human readable message>"}`.

| HTTP | When | Example `error` |
|---|---|---|
| 400 | Missing or invalid `relay`, `action`, `seconds`, or `id` | `"relay must be 1 or 2"`, `"action must be on or off"`, `"seconds must be 1-86400"` |
| 404 | `/timer/cancel?id=N` for an id that isn't active | `"no timer with id 7"` |
| 409 | Creating an 11th active timer | `"maximum 10 timers active"` |

The app turns these into plain messages: "Timer settings were rejected. Use 1 second to 24 hours.", "That timer is no longer running on the device.", "Maximum of 10 timers are already active on this device.", and "ESP200 is currently offline." for timeouts.

---

## 7. CORS and browser requirements

The app sometimes calls the ESP32 directly from the browser, so every response (including errors and 404s) must include:

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET, HEAD, OPTIONS
Access-Control-Allow-Headers: *
Access-Control-Allow-Private-Network: true
```

- Answer `OPTIONS` requests with **204** and these headers.
- Return `Content-Type: application/json` for all JSON responses.
- Respond fast (under 200 ms). The app times out after about 3 seconds.

## 8. Implementation notes (Arduino)

```cpp
struct Timer {
  bool     active;
  uint32_t id;
  uint8_t  relay;       // 1 or 2
  bool     turnOn;      // action: true = "on", false = "off"
  bool     repeat;
  uint32_t seconds;     // 1..86400
  uint32_t startedAt;   // millis() when this run was scheduled
};

const uint8_t MAX_TIMERS = 10;
Timer timers[MAX_TIMERS];
uint32_t nextTimerId = 1;   // never reset except on reboot

uint32_t remainingSeconds(const Timer& t) {
  uint32_t elapsed = millis() - t.startedAt;          // overflow-safe
  uint32_t total   = t.seconds * 1000UL;
  return elapsed >= total ? 0 : (total - elapsed + 999) / 1000;
}

void loopTimers() {
  // Fire in id order so "last one wins" is predictable.
  for (uint8_t pass = 0; pass < MAX_TIMERS; pass++) {
    int8_t next = -1;
    for (uint8_t i = 0; i < MAX_TIMERS; i++) {
      if (!timers[i].active) continue;
      if (millis() - timers[i].startedAt < timers[i].seconds * 1000UL) continue;
      if (next < 0 || timers[i].id < timers[next].id) next = i;
    }
    if (next < 0) break;
    Timer& t = timers[next];
    setRelay(t.relay, t.turnOn);                      // target state, idempotent
    Serial.printf("timer %lu fired: relay %u -> %s\n", t.id, t.relay, t.turnOn ? "on" : "off");
    if (t.repeat) t.startedAt += t.seconds * 1000UL;  // no drift
    else t.active = false;
  }
}
```

- Call `loopTimers()` from `loop()` together with `server.handleClient()`.
- `seconds * 1000UL` fits in 32 bits for 86400 s (86,400,000 ms).
- Use `millis() - startedAt` comparisons only; they stay correct across the ~49-day `millis()` rollover.
- Print create, cancel and fire events to Serial for debugging.
- Keep the relay pin logic (active-LOW or HIGH) exactly as the current sketch does.

## 9. How the app uses this API

| App action | Request sent to the ESP32 |
|---|---|
| Open app / every ~10 s while open | `GET /status` (shared for both relays on the same ESP32) |
| Turn Light / Fan ON or OFF | `GET /on?relay=N` or `GET /off?relay=N`, then `GET /status` |
| Start timer (only when `timerApi` ≥ 2) | `GET /timer?relay=N&action=on|off&seconds=S[&repeat=true]` |
| Cancel one timer | `GET /timer/cancel?id=ID` |
| Cancel All Timers (full firmware) | `GET /timer/cancel?id=…` for each of that relay's timers |
| Cancel Timers on This Relay (basic firmware) | `GET /timer/cancel?relay=N` |
| Connection test | `HEAD /` |

The app **never** calls `/timers/clear`.

The app's database stores each timer the user created, with the ESP32's `id` and the relay. If a timer disappears from `/status` (it fired, was cancelled elsewhere, or the ESP32 rebooted), the app marks it as ended. The countdown on screen ticks locally every second and is corrected at each `/status` sync.

## 10. Test plan

Run these from a computer on the same Wi-Fi (replace the IP if needed). Start with both relays OFF.

```bash
E=http://192.168.1.200

# 1. Version flag and shape
curl "$E/status"          # has "timerApi":2, "relays":[...], "timers":[]

# 2. Creating does not switch anything
curl "$E/timer?relay=1&action=on&seconds=20"
curl "$E/status"          # relay 1 still "off"; timer listed with id, action "on", remaining ~20
# ...after 20 s:
curl "$E/status"          # relay 1 now "on"; timer gone

# 3. Target state is idempotent
curl "$E/timer?relay=1&action=on&seconds=5"   # relay 1 already on
# after 5 s: relay 1 still "on", no flicker

# 4. Several independent timers
curl "$E/timer?relay=1&action=off&seconds=3600"
curl "$E/timer?relay=2&action=on&seconds=1800"
curl "$E/timer?relay=1&action=on&seconds=600&repeat=true"
curl "$E/timers"          # three timers, unique ids

# 5. Cancel exactly one
curl "$E/timer/cancel?id=<id of the relay-2 timer>"
curl "$E/timers"          # the other two remain
curl "$E/timer/cancel?id=99999"   # 404

# 6. Repeat keeps the same action
curl "$E/timer?relay=2&action=off&seconds=10&repeat=true"
curl "$E/on?relay=2"      # manual ON; timer must remain
# every 10 s relay 2 goes back to "off"; the timer stays listed

# 7. Relay-scoped clear really is relay-scoped
curl "$E/timer/clear?relay=2"   # only relay 2 timers gone
curl "$E/timers"                # relay 1 timers still there
curl "$E/timers/clear?relay=9"  # 400, nothing cancelled

# 8. Limits and validation
for i in $(seq 1 10); do curl -s "$E/timer?relay=1&action=off&seconds=900" > /dev/null; done
curl "$E/timer?relay=1&action=off&seconds=900"   # 409 once 10 are active
curl "$E/timer?relay=1&action=off&seconds=0"     # 400
curl "$E/timer?relay=1&action=off&seconds=86401" # 400
curl "$E/timer?relay=3&action=off&seconds=60"    # 400
curl "$E/timer?relay=1&action=maybe&seconds=60"  # 400

# 9. Clean up
curl "$E/timer/clear"
curl "$E/off?relay=1"; curl "$E/off?relay=2"
```

In the app, once `/status` shows `"timerApi": 2`, open **Light** or **Fan** → the timer form appears instead of the "needs a firmware update" note.
